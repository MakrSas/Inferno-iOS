## Установка билдов на iPhone

### iloader: «Failed to log in to Apple ID … HTTP 503 … GsService2»

**Причина — у Apple, не у вас.** С ~8–10 сентября 2026 сервер входа отбивает
любой запрос, в заголовке `X-MMe-Client-Info` которого клиент называет себя
`com.apple.dt.Xcode`. Так делают все сторонние сайдлоадеры — iloader, AltStore,
SideStore. VPN ни при чём: без него то же самое. Разбор —
altstoreio/AltStore#1790.

**Что делать:** ставить билды через **`~/Applications/iloader-fixed.app`** —
копию iloader 2.3.1, где эта строка заменена на `com.apple.accountsd/113.0.1100`
(той же длины) и приложение переподписано локально. Проверено: вход и установка
работают. Обычный iloader из `/Applications` так и будет давать 503.

- Когда выйдет официальное обновление iloader — `iloader-fixed.app` удалить.
- Оригинал не тронут. Копия до правки:
  `~/Library/Application Support/me.nabdev.iloader/claude-backup/iloader.app`.
- Править `/Applications/iloader.app` на месте нельзя: защита macOS
  «Управление приложениями» даёт `Operation not permitted`.
- Если Apple заблокирует и новую строку — проверить так (ответ `503` —
  заблокировано, `401` — проходит):

  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" -X POST -H 'X-MMe-Client-Info: <Mac15,7> <macOS;27.0;26A5378j> <com.apple.AuthKit/1 (com.apple.accountsd/113.0.1100)>' --data-binary t https://gsa.apple.com/grandslam/GsService2
  ```

### Прокси (FlClashX) и Apple

К ошибке 503 отношения не имел, но правила `DOMAIN-SUFFIX,apple.com,DIRECT` и
`DOMAIN-SUFFIX,icloud.com,DIRECT` добавлены в переопределение профиля (не в
подписку — она обновляется каждый час). «Обход домена» в настройках сети для
этого не годится: он действует только на системный прокси, а у вас TUN.
Копия прежних настроек: `~/Library/Application Support/com.follow.clash/claude-backup/`.

## Сеть в госте

### Интернет был, после перезагрузки гостя пропал

**Причина:** гость сам опускает свой конец USB-сети (`NETWORK_CONNECTION 0`,
`IONetworkController::disable`). Со стороны эмулятора это не лечится — проверены
все USB-способы.

**Что делать:** в приложении меню → «Поднять сеть в госте» (выполняет в госте
`/usr/sbin/ipconfig set en0 DHCP`). Приложение делает это и само, через полторы
минуты после старта, если адреса нет. Вручную в терминале гостя:

```
/usr/sbin/ipconfig set en0 DHCP
```

Проверка: `/usr/sbin/ipconfig getifaddr en0` должен ответить `10.0.2.15`.
`ifconfig` в iOS нет вообще.

### apt качает еле-еле

Сам канал даёт сотни КБ/с — медленный `apt`, а не сеть: он ждёт мёртвые
репозитории `apt.modmyi.com` и `cydia.zodttd.com`. Удалить их из источников.

## Передача файлов (меню → «Файлы»)

### «Шелл гостя не отвечает», а в консоли гостя видно `VAL… 1`

Шелл отвечал — приложение не читало ответ. У сокета консоли стоял таймаут чтения
20 с, и цикл чтения принимал первую же 20-секундную тишину за конец потока и
останавливался насовсем. Терминал при этом работал (он читает файл журнала), а
ответы для передачи файлов уходили в пустоту. Воспроизведено: старый читатель
вышел через 19 с тишины и ответа не увидел, новый дождался его на 25-й секунде.

Исправлено в сборке от 10 сентября, после 04:30. На старой сборке помогает только
перезапуск приложения — и то до первой долгой тишины.

### Требования

- в параметрах включён «Интернет через USB», и сеть в госте поднята;
- в госте стоит бутстрап с bash на консоли.

Отправленное ложится в `/var/mobile/Inferno/`, забранное — в папку `Guest`
приложения (видна в «Файлах»). Русские имена файлов работают.

### Переданный в гостя файл не виден в «Файлах» гостя

**Так и есть, это не поломка.** Файлы кладутся в `/var/mobile/Inferno/` — обычный
путь в ФС гостя, принадлежит root. «Файлы» в iOS показывают только iCloud Drive и
«На iPhone» (папки приложений), а произвольные пути — нет; «Фото» тоже не увидит
картинку, пока её не импортируют. Найти переданное:

```
ls -la /var/mobile/Inferno/
```

или через Filza. *(Отдельная задача: класть переданное туда, где «Файлы» его
показывают, и отдавать пользователю `mobile`, — не сделано, требует проверки на
стенде.)*

## Консоль гостя

### Команды не выполняются, в начале строки `>`

bash остался в незакрытой кавычке — длинная команда пришла покалеченной (занятый
гость теряет байты). **Нажать Ctrl-C.** В приложении это делается само при сбое
передачи.

### Никогда не посылать Ctrl-D и не писать `exit`

Демон bash на старых образах стоит без `KeepAlive`: выход из шелла закрывает
консоль насмерть до перезагрузки гостя. В `netlab/install-bootstrap.sh`
`KeepAlive` уже добавлен, но на установленных образах его нет.

## Cydia

### «Sub-process /usr/libexec/cydia/cydo returned an error code (2)»

**Причина найдена:** у `dpkg` нет базы пакетов.

```
dpkg: error: failed to open package info file '/var/lib/dpkg/status' for reading
```

Бутстрап держит базу в `/Library/dpkg` (она на месте, 812 строк в `status`), а
`dpkg` и `apt` ищут её в `/var/lib/dpkg`. Там должна быть ссылка, но `/var` в iOS —
отдельный том с данными, а `netlab/install-bootstrap.sh` распаковывал бутстрап
только в системный том. Каталога `/var/lib` в госте нет вовсе. `cydo` в порядке
(`-rwsr-sr-x root wheel`), дело не в нём.

Вторая половина причины: **корень гостя смонтирован только для чтения**
(`/dev/disk0s1s1 on / (apfs, local, read-only, …)`), а пакеты ставят файлы в
`/usr`, `/Library`, `/Applications` и пишут базу в `/Library/dpkg`. Одной ссылки мало.

Третья половина — **пакеты бутстрапа ни разу не настраивались**: их распаковали
из архива, а `dpkg --configure -a`, который джейлбрейк делает при первой
загрузке, никто не запускал. Поэтому `apt` при любой установке сначала лез
настраивать сам `dpkg` и падал.

**Починка — четыре команды в терминале гостя** (проверено на стенде по шагам):

```
mount -uw /
mkdir -p /var/lib /var/cache/apt/archives/partial /var/lib/apt/lists/partial && ln -sfn /Library/dpkg /var/lib/dpkg
/usr/libexec/cydia/firmware.sh
dpkg --configure -a
```

- `mount -uw /` снимает «только чтение» с корня. **Действует до перезагрузки
  гостя** — после неё команду надо повторить, иначе Cydia снова упадёт.
- Ссылка и каталоги — навсегда (том с данными).
- `firmware.sh` регистрирует пакет `firmware`, без него пакеты не ставятся
  (`PreDepends: firmware (>= 11.0) but it is not installable`).
- `dpkg --configure -a` донастраивает бутстрап — `coreutils`, `ncurses`, `gnutls`,
  `gnupg`, `apt` и другие. Нужно один раз.

После этого `apt-get install unzip` проходит чисто. Команды набирать по одной:
длинную строку занятый гость может покалечить.

**Про `cydo` (проверено на стенде 10 сентября, модель Opus 4.8):**

- `cydo` — не обёртка над произвольным `dpkg`. Это setuid-помощник с проверкой
  вызывающего: любой процесс, кроме самой Cydia, он отбивает сообщением
  `none shall pass`. Поэтому путь Cydia **нельзя воспроизвести из шелла** —
  `su mobile -c 'cydo …'` тоже даёт `none shall pass`, это не та ошибка.
- Значит `code (2)`, который видит пользователь, — это код выхода `dpkg`
  **внутри** разрешённого вызова Cydia, а не отказ `cydo`. Настоящую причину
  печатает `dpkg` строкой выше, но Cydia её прячет.
- `dpkg` напрямую от root после четырёх команд выше на стенде отрабатывает
  начисто: `dpkg --configure -a` настраивает пакеты, `apt-get install unzip`
  ставит без ошибок. То есть лечится именно приведением состояния в порядок.

**Важное наблюдение с телефона:** там `firmware.sh` и `dpkg --configure -a`
вернулись **без единой строки вывода** и мгновенно — а на стенде `firmware.sh`
идёт ~20 с и печатает строки, `dpkg --configure -a` печатает «Setting up …» для
десятка пакетов. Пустой мгновенный вывод почти наверняка значит, что команды не
выполнились (покалечены при вводе или корень остался read-only). **Проверяйте по
выводу:** если этих строк нет — команда не сработала, повторите её.

**Не проверено сквозняком:** сама установка через Cydia после починки на стенде
не воспроизводилась (мешает защита `cydo`). Проверка — состояние `dpkg`:
`dpkg --audit` должен молчать, `dpkg -l | grep -c '^ii'` — расти. Если чисто, а
Cydia всё равно падает — прислать вывод `dpkg --audit` из терминала гостя.

Попутно: источник bingner подключён дважды (`bingner.list` и `cydia.list`), а
`cydia.zodttd.com` отвечает 308 — это только предупреждения, на установку не
влияют.

## Запуск и состояние машины

### Паника SEP `sks … [nvilv]`

Диск и состояние SEP из разных «поколений» — например, после того как «Файлы»
заменили часть файлов, а часть оставили старыми (дубликаты вида `sep_ssc 2`).
Состояние гостя нельзя откатывать частями: `root.qcow2`, `sep_nvram`, `sep_ssc`,
`nvram`, `effaceable`, `ctrl_bits`, `syscfg` кладутся только набором из одного
места. Подробно — `FINDINGS.md`.

### Как выключать

Только меню → «Выключить машину» (QMP `quit`). Смахнуть приложение — значит
оборвать запись на диск, и следующий запуск стартует рассогласованным.

### Чёрный экран / машина не стартует

JIT включать через StikDebug **до** запуска машины.

### Другое разрешение экрана

Машина его принимает, но iOS при нём картинку не выводит — поэтому выбора в
приложении нет. Только родное 828×1792.
